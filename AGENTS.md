## Numerical parity and hardening

Before modifying the imported numerical code, capture tolerance-based golden outputs from the
minimal port for deterministic AR(1) and AR(2) traces. Preserve the comparator's existing tests for:

- AR(1) execution and recovery.
- AR(2) execution and recovery.
- automatic `g` and `sn` estimation.
- rejection of integer input.

Then address these known issues with dedicated regression tests:

- `deconvolve(..., b=<value>)` currently ignores the supplied baseline; it only disables baseline
  optimization. Define and implement correct supplied-baseline semantics.
- AR(2) with `optimize_g > 0` mutates `g`; tuple input can therefore raise `TypeError`. Normalize to
  an appropriate mutable internal representation without mutating caller-owned input.
- Unsupported `g` lengths currently print and return `None`; raise a clear exception instead.
- Lists, empty arrays, non-1-D arrays, NaNs, infinities, constant/degenerate traces, and short traces
  need explicit validation or documented handling.
- Automatic AR estimation replaces unstable roots using global `np.random.normal`, making nominally
  identical runs and cache entries potentially nondeterministic. Remove uncontrolled randomness or
  expose and record a deterministic seed/strategy.
- Direct constrained decimation can fail when trace length is not divisible by `decimate`. Define
  trimming/padding behavior and test it.
- The facade routes AR(1) through compiled constrained OASIS but AR(2) through Python ONNLS, even
  though compiled AR(2) routines exist. Preserve current behavior for parity first, then explicitly
  choose and document the supported AR(2) backend.
- The facade defaults to penalty mode `0`, while the comparator tests explicitly use `1`. Select and
  document the framework default rather than inheriting it silently.

Avoid unrelated rewrites of the numerical core. Keep parity changes and semantic fixes in separable
commits whenever practical.

## Framework adapter contract

OASIS accepts a one-dimensional, uniformly sampled trace and has no timestamp input. Therefore:

- Run deconvolution independently for every `TrialSeries`.
- Never concatenate epochs before deconvolution; doing so leaks calcium state across trial gaps.
- Concatenate/sort outputs only after each trial has been processed.
- Validate near-uniform sampling or resample explicitly. Do not silently treat an irregular trace as
  uniform after finite-value filtering.
- Treat `g` as a per-bin coefficient. If preprocessing changes the sampling rate, either estimate it
  on the processed trial or derive it from a physical time constant. Include the final values and
  sampling rate in metadata and cache configuration.

Map the OASIS return tuple `(c, s, b, g, lam)` into `MethodResult` as follows:

- `name="oasis"`.
- `time_stamps`: the processed per-trial timestamps, concatenated after inference.
- `spike_prob`: `s`, the continuous nonnegative deconvolved event amplitude.
- `reconstruction`: `c + b`, assuming the finalized low-level baseline contract confirms that `c`
  excludes the baseline.
- `discrete_spikes`: `None` initially.
- `metadata`: serialized config plus per-trial estimated/final `b`, `g`, `sn`, `lam`, sampling rate,
  solver/backend information, source version, cache tag, and cache key where available.

OASIS `s` is not a calibrated probability or an integer spike count. Do not copy raw `s` into
`discrete_spikes`: C-SPIKES downstream code sums and rounds that field when reporting spike counts.
Only add discrete output after an explicit event-threshold/count policy has been specified,
documented, and tested. Continue using `spike_prob` for correlation evaluation, matching the broad
continuous-prediction convention already used by other backends.

## Cache requirements

Reuse `src/c_spikes/inference/cache.py`; do not create an OASIS-only cache format.

The cache identity must cover every inference-affecting choice, including:

- AR order and final/provided `g`, or time-constant strategy.
- noise `sn` value or estimation strategy.
- baseline value/optimization/nonnegativity policy.
- `optimize_g`, penalty mode, decimation, and other exposed solver options.
- preprocessing/downsampling/resampling policy and effective sampling rate.
- OASIS source/adapter version.
- trace content and trial boundaries/lengths.

Do not hash only a flattened trace: OASIS depends on where trials reset, so identical samples with
different trial partitions must not share a cache entry. Test cache hits for identical inputs and
invalidation for parameter, preprocessing, trace, and trial-boundary changes.

- A normal C-SPIKES build installs and imports `c_spikes.oasis.oasis_methods` without an untracked

  summary, and comparison manifest.

- Provenance, attribution, build instructions, parameter semantics, and current limitations are
  documented.
